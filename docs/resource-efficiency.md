# Adaptive resource policy

> **Status:** Design and measurement draft. Items marked **Planned** are not implemented. The
> current-behavior notes describe the PR base source; resource savings have not been measured or
> verified on an installed build.

Reel reduces optional work when macOS reports memory pressure, Low Power Mode, or elevated thermal state. The policy is event-driven; it does not poll. It leaves active playback, decoder settings, Live Captions, and AirPlay buffering and synchronization unchanged.

## Current behavior

- Thumbnail decoding is deferred while resources are constrained. A request deferred this way resumes when the system returns to nominal conditions and its player still has visible media.
- Closing a main or mini-player window requests cancellation of thumbnail decoding, invalidates pending thumbnail callbacks and cache reads, and clears Live Text analysis.
- When a player window closes while playback is already idle, Reel drops its in-memory thumbnail arrays and preview-image references and suspends the mpv render context as soon as the window has closed and pending AirPlay commands have drained. After playback stops while a window remains closed, the same cleanup runs after a 60-second grace period. Cleanup is ineligible while there is a pending open, background player task, visible main or mini-player window, picture-in-picture session, pending mpv file start, or undrained AirPlay command. The mpv core remains alive. App media-start commands preflight renderer recovery before submission. Every mpv file start is also held at `on_before_start_file` until the main thread cancels idle cleanup and restores the render context if needed, including input.conf and IPC loads. The renderer cleanup ticket ends at `START_FILE`, shutdown, or a changed current playlist entry. A separate stop-completion marker remains through `START_FILE` and until a generation-matched `idle-active` transition returns to idle, so Stop can complete even when it races delivery of the start event to PlayerCore. The low-traffic client observes `idle-active` independently of the primary ring and only completes a ticket after that start has left idle and later returned; a delayed initial idle notification cannot retire a new ticket. This also reconciles normal end-of-file state if the primary ring drops its property event. A later pre-start hook supersedes abandoned tickets. Stop saves cached resume values on AppKit, then performs the optional watch-later write off the main thread after AirPlay restores drain and submits Stop asynchronously. Quit is handed off to its shutdown worker after the same restore barrier. This keeps AppKit available for a pre-start continuation even if libmpv is holding its core. User-open option updates, the replacing `loadfile`, and any batch playlist appends run serially on a worker; their order does not depend on libmpv asynchronous request ordering. A replacement requested during a pre-start hook is stopped and drained after the hook continues rather than waiting for the current file to reach natural EOF. The fence has no elapsed-time expiry because another async hook may legitimately hold the load. A low-traffic secondary mpv client carries renderer replies and the generation-matched `idle-active` transition independently of AirPlay and property traffic on the primary event ring. During a first-window restore, the CGL pixel-format options are read from a post-initialize cache, and `force-window=immediate` is written asynchronously before the hook continues. This releases PlayerCore's references; FFmpeg's own thumbnail arrays are released after the serial FFmpeg operation settles, so an input that ignores interruption can delay their release. Stop completion and late background-task completion start a fresh delay when cleanup was deferred. A new open invalidates the delayed cleanup.
- A macOS memory-pressure warning or critical event also releases eligible idle thumbnail previews and the idle render context promptly. Active playback and visible renderers are ineligible. The on-disk thumbnail cache remains available for the next open.
- Thumbnail-cache directory listings are reused until a cache file is created, updated, deleted, or cleared. A directory modification-date check notices changes made by another Reel process. Directory scans, file-stat calls, sorting, and deletion run outside the cache-state lock; each process runs only one eviction at a time, and a concurrent local eviction request queues one coalesced retry. Separate Reel processes may evict concurrently; if another process removes an entry from the same snapshot, that deletion counts toward this process's target. Active staging files count toward the configured cache size. Exact-name orphan staging files created before this launch are removed during launch; another sweep runs after a Reel process exits and removes files older than that sweep, once no other Reel process can own them.
- Thumbnail cache metadata includes the selected preview width. A width change invalidates in-flight work, removes old cache files, and regenerates previews for active video players.
- Active playback is not stopped or reconfigured by the resource policy. AirPlay command queues and timing remain under the bridge's existing lifecycle.
- A Stop request cancels the remaining app-open playlist appends after the currently executing mpv command returns. A newer open supersedes a queued older open, and Quit invalidates queued opens before mpv shutdown. This bounds cancellation delay for very large selections and avoids an extra synchronous renderer-restore hop for each item appended after the first load.
- A Stop waiting for the AirPlay restore queue is tied to its pending media-start ticket or active pre-start hook. If that hook publishes its ticket after Stop begins, Reel binds Stop to the in-flight start; a later raw IPC or input.conf start supersedes the Stop while it is still pending, and further replacements carry the stopping-state handoff to the latest start. Once mpv has accepted the global Stop command, Reel cannot retract it; a raw start racing that accepted command still depends on mpv command scheduling.

## Why renderer suspension is separate

Two read-only samples came from the running installed Reel 1.5.0 (188) process, before build 189 was launched. At about 19:08 EDT, the process showed a 663.1 MB physical footprint, 389.0 MB of malloc allocations, 438.5 MB swapped out, and 145.1 MB resident in IOSurface. The user confirmed that this sample was taken with the main window closed and playback stopped with no file loaded. A later read at 19:37 EDT showed 540.0 MB footprint, 321.2 MB malloc allocations, 532.2 MB swapped, and 93.8 MB resident IOSurface. The later reading was not a controlled before/after experiment and cannot be attributed to candidate changes. These categories overlap and do not identify allocation owners. A separate `heap` observation reported 339.9 MB as non-object allocations without allocation backtraces; its capture time and relationship to either vmmap sample were not recorded. Installed build 188 retained its mpv core and render context while idle. The IOSurface measurement makes renderer resources a plausible contributor, not an attributed cause. Candidate source frees the eligible idle render context after a grace period, or immediately after an already-idle window closes and queued AirPlay commands drain, while keeping the mpv core for reuse. A candidate before/after profile and reopen checks are still required to prove IOSurface reclamation and correct video, audio-only, PiP, plugin, and AirPlay transitions.

## Broader resource design

The governor uses event signals and protects media work with different costs:

| Signal or state | Current or planned response |
| --- | --- |
| Windowless idle player | Current: closing a window while already idle immediately purges optional preview references and suspends the reusable render context after pending AirPlay commands drain; other idle transitions use a 60-second grace period. The mpv core remains alive. Planned: identify remaining non-object allocation owners and measure IOSurface reclamation. |
| Memory warning or critical pressure | Current: purge eligible idle preview caches, suspend idle render contexts, and defer thumbnail work. Planned: cap retained player contexts and measure allocator reclamation. |
| Low Power Mode or non-nominal thermal state | Current: defer thumbnail decoding and resume it after conditions recover. Planned: limit optional analysis and metadata concurrency using process-wide work budgets. |
| Active playback or AirPlay | Keep decode, output, display-link needs, route synchronization, and buffering under their existing playback-specific controls. Do not rewrite user decoder or audio settings. |
| Idle background work | Current: cancel thumbnail reads and cache writes by request generation; FFmpeg thumbnail opens and reads use a cooperative interrupt callback. A protocol that does not honor FFmpeg interruption may finish later. Planned: give playlist metadata probes explicit cancellation and bounded network I/O. |

The next performance review should measure CPU time, physical footprint, allocator bytes, swapped pages, IOSurface bytes, disk/network work, and reopen latency separately. Renderer suspension may reduce IOSurface use, but no candidate before/after profile has demonstrated a reduction in physical footprint, malloc allocation, or IOSurface bytes. The two different readings from build 188 are not a controlled comparison. This operation does not destroy the mpv core and therefore may leave much of the retained heap intact. Allocation-stack evidence and controlled before/after profiles are required before claiming that renderer suspension fixes this report.

## Acceptance observations

On a development build, record process footprint, malloc allocations, swapped pages, RSS, and IOSurface before and after closing a video window with no file loaded. Confirm the render context is recreated before reopening video, then repeat with thumbnail generation and Live Text analysis in progress. Apply memory pressure while another player is active. Confirm active playback, AirPlay stream continuity, PiP, and Touch Bar controls remain responsive. A smaller RSS alone does not prove retained heap or IOSurface memory was released.
